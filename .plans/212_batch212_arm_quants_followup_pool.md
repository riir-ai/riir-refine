## The surviving lead (why this batch exists)

The **b2b-LUT CPU face** of an owned GPU law. `lut-free-bit-spread-vadd4-unpack` (kernel_opt, mined from PrismML's CUDA mmq-hopper-q1.cu @ e311ed38) owns: expanding packed sub-byte weight fields into byte lanes in a hot loop must NOT use a `__constant__` LUT — divergent per-lane indices serialize the constant cache (~1.7× end-to-end); ALU bit-spread instead. **The same file's CPU q1_0 kernel uses exactly the LUT form** — and the contrast is the content:

- The GPU law's mechanism is `__constant__`-memory serialization under DIVERGENT per-lane indices. The CPU b2b form (`table_b2b_0[bits[k]]` → u64 → `vcreate_u8`) is SCALAR sequential byte-indexed loads: one index per load, no divergence, no constant-cache semantics — a 2 KB table pair hot in L1.
- It buys 8 expanded lanes per scalar load (vs an 8-op shift/mask/sign-fold chain), then `>>4` → 0/1 and `2v−1` folds the sign per VECTOR (2 ops per 16 lanes), not per element.
- Two consumers share ONE table pair: q1_0_q8_0 (full 1-bit value expansion, `table_b2b_0`) and q5_0/q5_1 (the 5th-bit mask via the INVERTED table, `table_b2b_1 = { B8(10,00) } // (!b) << 4` — comment verbatim "extract the 5th bit via lookup table ((!b) << 4)"), the latter through scalar `tmp[]` u64 staging then `vld1q_s8`.
- The ternary kernels (tq1_0/tq2_0) deliberately stay arithmetic (`vhaddq_u8(q, q>>1) >> 6`, 17 sites — the B211-rider identity; `k_shift {1,3,9,27}` + multiply-by-{3,9,27,81} for upper trits) — the LUT/ALU boundary is DENSITY-aware in-tree: 1-bit→LUT, 3-state→ALU.
- rider = count-neutral (kernel_opt stays 777); no rust_perf rule (a new rule would add a THIRD staged M3 GOAT to the quiet-box queue while two wait — the B209 single-rider precedent is the disposition).
