# MIL program + weight-blob formats that work on macOS 26.5

> The single most expensive lesson of the T0 spike: FOUR plausible MIL
> variants from three independent external projects all failed with
> `InvalidMILProgram` before the working one compiled. The differences are
> SUBTLE and mostly not semantic. This file records the exact working text
> and every known-failing variant with the reason.

## The working single-conv program (fp16, byte-verified)

Generated by `fp16_linear_mil(ic, oc, sp)` in riir-poc `ane_t0.rs`;
byte-identical (diffed) to maderix `ane_int8_bench.m`'s `genMILFP16`
output, compiled + evaluated on M3 Max / macOS 26.5.2 with cosine 1.000016
vs a CPU fp16 reference:

```text
program(1.3)
[buildInfo = dict<string, string>({{"coremlc-component-MIL", "3510.2.1"}, {"coremlc-version", "3505.4.1"}, {"coremltools-component-milinternal", ""}, {"coremltools-version", "9.0"}})]
{
    func main<ios18>(tensor<fp16, [1, __IC__, __SP__, __SP__]> x) {
        string c_pad_type = const()[name = string("c_pad_type"), val = string("valid")];
        tensor<int32, [2]> c_strides = const()[name = string("c_strides"), val = tensor<int32, [2]>([1, 1])];
        tensor<int32, [4]> c_pad = const()[name = string("c_pad"), val = tensor<int32, [4]>([0, 0, 0, 0])];
        tensor<int32, [2]> c_dilations = const()[name = string("c_dilations"), val = tensor<int32, [2]>([1, 1])];
        int32 c_groups = const()[name = string("c_groups"), val = int32(1)];
        tensor<fp16, [__OC__, __IC__, 1, 1]> W0 = const()[name = string("W0"), val = tensor<fp16, [__OC__, __IC__, 1, 1]>(BLOBFILE(path = string("@model_path/weights/weight.bin"), offset = uint64(64)))];
        tensor<fp16, [1, __OC__, __SP__, __SP__]> c0 = conv(dilations = c_dilations, groups = c_groups, pad = c_pad, pad_type = c_pad_type, strides = c_strides, weight = W0, x = x)[name = string("c0")];
    } -> (c0);
}
```

## The three load-bearing syntax gotchas

1. **`{{ … }}` double braces in buildInfo are LITERAL and REQUIRED.**
   maderix builds the header with `appendString:` (no printf processing),
   so their `{{` survives verbatim into the compiled text. omlx builds it
   with `stringWithFormat:` where `{{` collapses to `{` — single braces.
   **Both forms appear in "working" external code, but on macOS 26.5 only
   the double-brace form was ever observed to compile here.** If a MIL
   fails with `InvalidMILProgram` and looks right, count the braces first.

2. **`name = string("x")` with spaces around `=`** (maderix style). The
   omlx no-space `name=string("x")` style was never observed to compile on
   this box. May be cosmetic — never got a clean A/B because the brace fix
   landed with it — keep the spaced form.

3. **Conv input layout is `[1, C, H, W]` with the sequence on the SPATIAL
   axes** — the 1×1 conv IS the linear layer (y[o,h,w] = Σᵢ x[i,h,w]·W[o,i]).
   omlx's format strings suggest `[1, ic, 1, seq]` (H=1) — reading their
   `%d` argument order carefully shows their tensors are also
   channels-first with seq on the W axis; the `[1, ch, sp, sp]` SQUARE
   spatial form is what is verified on this box (sp=64 and sp=256).
   **Non-square H×W (e.g. 2048×1 for a 2048-token block) is UNVERIFIED —
   flagged as a T2 risk in Issue 726.**

## Variants tested (2026-08-19, all through the same bridge)

| Variant | Source | Result on 26.5 |
|---|---|---|
| fp16 conv, `[1,ic,1,seq]`, no-space attrs, single-brace buildInfo | omlx `fp16_linear_mil` | **FAIL** `InvalidMILProgram` |
| fp32-in → cast fp16 → conv → cast fp32, `[1,ic,1,seq]` | maderix docs `mil_gen_conv` | **FAIL** |
| dynamic matmul, slice/reshape/transpose, weights as input, no BLOBFILE | rane 0.2.0 `mil::matmul` | **FAIL** (note: rane's BLOBFILE path was never hardware-proven — their example passes `&[]` weights) |
| int8 + `constexpr_blockwise_shift_scale` + separate scale blob | omlx production form | **FAIL** (from the pure-Rust bridge; not re-tested through the ObjC bridge) |
| fp16 conv `[1,ch,sp,sp]`, spaced attrs, `{{}}` buildInfo | maderix `ane_int8_bench` | **PASS** (cosine 1.000016) |

The four FAILs were all run through the pure-Rust bridge, which is itself
the confound (see `rust_bridge_negative_result.md`) — but the byte-identical
bisection (their exact mil + blob through our bridge vs their binary) proved
the bridge was the difference for THOSE runs. Only the PASS row is
guaranteed-clean evidence about the format itself. Treat the FAIL table as
"suspect, re-verify through the ObjC bridge before relying on the failure".

**Deployment-target tag:** `<ios18>` works. `<ios26>`, `<ios19>`,
`<macos26>` were tried (all still failing, but through the broken bridge —
target tag is probably not the discriminator; `<ios18>` is what the
verified program uses).

## Multi-procedure banks: REJECTED on macOS 26.5

omlx's bank form — N named functions `func procedureNNN<ios18>(…)` in ONE
program, selected at request time via `procedureIndex:` +
`inputSymbolIndicesForProcedureIndex:` — **fails ANECCompile on this box**
with `InvalidMILProgram`, tested with both `procedure000` (omlx `%03zu`
padding) and `procedure0` naming, with the working single-conv body inside.
This is a REAL format-level failure (through the ObjC bridge, which
compiles the single-func form fine). omlx's banks compiled on their
macOS (M3 Ultra) — the bank syntax is macOS-version-sensitive.
**Consequence:** per-layer single-procedure programs are the M3-Max-safe
shape; procedure banking needs re-derivation before use (Issue 726 T2).
The request-side plumbing for procedure indices (symbol-index lookup +
`procedureIndex:`) is implemented and ready in the spike regardless.

## The weight-blob binary format

Two layers: a 64-byte GLOBAL header, then one or more 64-byte CHUNK
headers each followed by payload. Matches rane `pack_weights`, omlx
`make_blob`, and maderix `mil_build_weight_blob` (byte-compared):

```text
Global header (64 B):
  [0]  = 0x01
  [4]  = 0x02
  (rest zero)

Chunk header (64 B), first chunk starts at offset 64:
  [0..4]  = EF BE AD DE          (magic, LE "deadbeef")
  [4..8]  = 0x00000001           (type)
  [8..16] = payload byte count   (u64 LE; omlx writes u32-width, tolerated)
  [10]    = element bit-width    (0x10 = fp16, 0x08 = int8 — maderix sets it;
                                   NOT set by rane/omlx single-blob; setting it
                                   did not fix or break anything on 26.5)
  [16..24] = ABSOLUTE byte offset of this chunk's payload (64+64=128 for
             a single-chunk blob)

Payload: raw elements (fp16 = 2 B each, int8 = 1 B)
```

The MIL's `BLOBFILE(..., offset = uint64(N))` points at the CHUNK HEADER
(N=64 for the first chunk), not at the payload — the loader reads the chunk
header to find the data.

**Multi-chunk (bank) blobs:** chunks are 64-byte-ALIGNED; each chunk's
header records its own absolute payload offset; MIL references each chunk
header's offset (omlx `append_blob_chunk`). Bank blobs were never
compile-verified on this box (bank MIL rejected) — the packing code exists
in `pack_bank_blob()` and is unit-tested for layout only.

**fp16 element order:** row-major `[oc, ic]` weight matrix as-is — the
conv weight tensor IS the matrix; no transpose needed (verified by the
numerics gate). For backward passes maderix transposes when building the
blob instead (W^T as `[in, out]`).

## IOSurface I/O layout

Surfaces are byte-sized 1-D allocations (`Width=bytes, Height=1,
BytesPerElement=1, BytesPerRow=bytes, AllocSize=bytes, PixelFormat=0`) —
NOT shaped by the tensor dims. The procedure's tensor shape interprets the
bytes. Element count for a `[1, C, H, W]` fp16 tensor = C·H·W, bytes = ×2.
Lock (`IOSurfaceLock`) before CPU read/write, unlock after. Practical
surface cap ~256 MB (rane).
