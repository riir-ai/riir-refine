## Why (the verdict's reasoning)

Promoting with G3 failed (+69% cold vs the +5% bar) would be rewriting a bar after seeing it fail — the habit the GOAT gate exists to stop. But the 233 ms is spent AFTER the work is done: the matcher is already built, the scan already printed — the cost is encode + blake3 + the 18.8 MiB write on the exit path. Three fixes, all small:

- [x] T1 — **Store after print** — **LANDED** (commit below): `index_cache::store_deferred` hands encode + write + prune to an `index-cache-store` thread at matcher build; `finish_pending_stores()` joins it as the LAST statement of `heal` main (after results, roll-up, footer) and prints the one `[index-cache] stored … (after results)` line. Spawn failure is LOUD + skips the entry (next miss rewrites). A run dying via `process::exit` before the join loses only the entry; its `.tmp-*` litter is swept by `prune` once ≥ 1 h old (a live writer's tmp is never touched). Tests: `deferred_store_lands_identical_entry_after_join` (byte-identical file vs inline `store`), `prune_sweeps_only_stale_tmp_litter`; the G1 test joins before reading the dir. Original text:: move the cache store (encode + write + prune) OFF the critical path — the results are printed first, the store runs on a thread joined at process exit (a detached write risks being killed mid-entry; the join keeps the atomic-rename contract). Time-until-results then matches OFF; total wall-clock recorded alongside. The print-then-store order must keep the stderr disclosure lines AFTER the run-end roll-up (one `[index-cache] stored …` line, still G4's size report).
- [x] T2 — **Drop the extra buffer copy** — **LANDED** (same commit): `Enc` is one pre-sized buffer (`estimated_len` capacity hint — no doubling re-copies), section length prefixes reserved + patched in place, ONE `blake3::hash` over the finished buffer (the 224 shape also hashed every section TWICE — the inner Enc's hasher was dead work). Wire bytes unchanged (no format bump). Original text:: `encode_domain` builds a temp `body` buffer for the length prefix, then memcpy's it into the outer buffer (≈2× the 18.8 MiB). Patch the length prefix in place instead (reserve 4 bytes, remember the offset, `copy_from_slice` the length after the payload lands). Halves the encode wall cost; a thread-joined store still wants it (exit latency).
- [ ] T3 — **Cache size cap + eviction**: `KEEP_ENTRIES` (8) bounds the ENTRY COUNT, not the BYTES — at 18.8 MiB per corpus state and ~2 new states/day, an unpruned machine accrues ~7 GB/year if entries churn faster than prune... actually prune DOES bound count at 8 (~150 MiB ceiling) — the cap work is (a) pin the ceiling in bytes too (`RIIR_REFINE_INDEX_CACHE_MAX_MB`, default ~256, evict oldest-first beyond it) and (b) verify prune's mtime ordering survives the touch-on-hit (an entry pinned by constant use must not starve a fresh corpus state — LRU vs LFU decision recorded at implementation).
- [ ] T4 — **Re-run G3 on a quiet amo** with the restated bar: time-until-results ≤ +5% vs OFF (total wall-clock disclosed beside). PASS ⇒ promote `index_cache` to the release set + default IN THE SAME COMMIT, `RIIR_REFINE_INDEX_CACHE=0` the demote switch (env-switch law); FAIL ⇒ back to the verdict with the numbers.
