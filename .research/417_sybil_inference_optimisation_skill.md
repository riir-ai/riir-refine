## The ceiling.py finding (needs-validation, P2)

`decode_ceiling`'s return — `bandwidth / ((verify + draft) / (accept * n)) * n` — double-counts concurrency: `verify` already carries the per-stream KV term (`n * kv_bytes * ctx`) and the draft term is `drafts * n * (...)`, so bytes-per-step is aggregate; aggregate tok/s is `bandwidth * (accept * n) / bytes_per_step` and the trailing `* n` multiplies concurrency a second time (at n=2, drafts=0: 4×B/bytes vs the correct 2×B/bytes). Their own prose contradicts it: "the aggregate ceiling therefore grows almost linearly with N" — the code grows ~quadratically at small n. Secondary quirk: draft weights are counted `× n` (per-stream) while dense weights are read once per step for all streams — under a batched draft forward the draft weights are shared like dense. UPSTREAM: present at the pin (their landed code — decision-content finding, never a PR from this verdict). If the league adopts ceiling arithmetic (below), re-derive the formula from first principles rather than porting this line; the finding is recorded for the upstream report the owner may choose to send.
