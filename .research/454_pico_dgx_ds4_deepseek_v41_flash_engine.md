## What the page is, and what it is not

The page is a vendor benchmark post. Per the serving-recipe class note its own unit of value is the qualified configuration, not kernels — graded on the lane axis. Three honesty findings about it, from the repo it cites:

1. Its "controlled replay test" anchor (`engine.md#L2229-L2243`) is a **two-row table of the repo's own front-end bench** (`engine.md:2241-2242`: cold prefill tok/s at 945 / 3,747 / 16,419 / 28,654 / 57,542 tokens — dsgb10 with CED 2,738 / 5,645 / 6,906 / 7,221 / 7,221; the same, exact (`--exact`) 2,125 / 3,575 / 3,710 / 3,777 / 3,737), k = 1, greedy, "nothing else on the GPUs". The page's "3,737 to 7,221 tok/s on the same 57,542-token prompt" is that table's two rows — a self-reported A/B, not a third-party controlled test. The numbers are real; the framing is generous.
2. The technique the page adopted ("decoder sliding-window attention bounded replay" — Ciru: "We added bounded replay to Ciru after seeing Pico's results") is **model-sanctioned but NOT bit-compatible** (`docs/ced.md:15-16`: "The model was post-trained with the replay simulated (§3.2.2). So CED is a sanctioned way to run the model, but it is not bit-compatible with `model.py`"; `:93-94` KL 0.0004–0.012 nats, "3–15× a numerics twin's"). The page carries the sanction and omits the KL.
3. The page's comparison rows are **cross-silicon, cross-prompt, cross-timing-boundary** and say so in footnotes ("Each system used its own prompt"; "Ciru times native generation and Pico times the stream"; "The suites used different prompts"; 1/1 vs 3/3 facts retrieved). Every absolute tok/s number on it is provenance, never headroom — the absolute-numbers caveat, fully in force.
