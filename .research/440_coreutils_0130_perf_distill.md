## The attribution finding (the controlling caveat)

**No measured number appears in any diff read.** The release notes quote `basenc` base58 ~35×, `cut` +23%, `date` +22%, `join` +20%, and the `uucore` buffered-reader PR title says "+8%"; none of these figures is present in the commit diffs, and the `tr` and `od` perf claims carry no number at all. Every figure in this note is therefore PROVENANCE, never a bar. The only in-source magnitude claims are two comments — `tr`'s "doubling the time of `tr -s`" for the out-of-line write and `sort`'s "pure overhead here" for the lazy merge comparator — both unquantified. The batch's G2 cells must measure from first principles on our validator; nothing transfers.

A second finding: the release notes UNDER-report the perf work. The `tr` speedup is a four-commit series (density-tiered delete, single-byte classification hoisted to the constructor, zero-hit chunk returns the input borrow, out-of-line write), and the `sort` lazy-key merge, the `expand`/`unexpand` plain-run fast path, and the `ls` DFS release fix appear nowhere under "Performance". A title/release-notes-only pass would have missed the two strongest candidates.

What is genuinely new is NARROWER than the release notes make it read, and the verdict round made this precise: one composition refinement of an owned law (R1 — the density CHOICE is owned as a feedback latch; R1 owns the exact-count tier, the survivor-rate per-block switch, and the zero-hit borrow), one unowned-adjacent regime (R2 — std's `sort_by_cached_key` has ZERO corpus owners, and the merge-specific k-regime rides it), and four decision/alloc candidates.

## GOAT candidate test (R1, the single strongest benchable)

1. **Benchable** on the perf-bench Pareto validator + exact alloc axis — yes, over FOUR arms = THREE baselines + the tiered arm: the naive per-byte table filter (G1's oracle), memchr-run-copy ALONE, branchless compaction ALONE (the two single arms that could each win their own regime outright), and the tiered form itself. The tiered form must hold in one sentence: at every density and every size [1K, 16K, 256K] it is never slower than the best single arm and beats each single arm inside that arm's own regime — otherwise the fixture proved SIMD, not tiering, and R1 demotes to a face on `prefilter-skip-density-demotion`. All arms alloc-free into a pre-sized sink.
2. **Exact semantics** — yes, byte-identical output (a filter is a filter; integer/byte only, no tolerance strategy needed).
3. **Magnitude story** — mechanism-level: the sparse tier replaces a per-byte table load + branch with a SIMD `memchr` over the runs; the survivor-rate switch removes a ~50%-mispredicted branch per byte in the mid-density regime. Weaker than a cycles-of-division argument, and the four thresholds (128, `FEW` 64, `BLOCK` 1024, the 256-byte first guess) are unmeasured upstream.
4. **Deterministic** — yes.

R2 passes the same four **on the corrected axis** (verdict round 1): a counter-wrapped expensive key over a k-way merge of sorted runs vs a `sort_by_cached_key`-shaped arm, order-identical by the stated construction, deterministic — with key MATERIALIZATION cost (allocations + bytes of key material built vs bytes the comparisons inspect) as the primary axis, key-eval count a secondary column only, because at k≥2 a lazy heap merge's ~n·log₂k comparisons × 2 key reads exceed n and a count-based bar would fire for the wrong reason.

Criterion-1 fails for **R3 alone** for a DOMAIN reason (kernel link resolution) — genuinely decision-only, the `NotBenchable` annotation class, not a demotion. **R6 is benchable-with-fragility** (time the hot loop with the write inlined vs out of line; compiler-dependent — a fragile cross-version win demotes to a face) and **R7 is benchable** (count metadata calls: one lstat vs two stats). R4 and R5 are benchable on the alloc/complexity axes.
