## Ranked candidates

1. **`launch-time-code-as-data-l2-warm`** (D — dispatch/code-placement; the GOAT lead, B). A megakernel's text exceeds every instruction cache on the path: layer text is 200–320 KB ("Text size: a layer's 200-320 KB of text is fetched again at every launch, and only about the first 64 KB arrives with the launch (the code prefetch loads the rest into L2)" — kernels/README.md), the SM icache is ~128 KB and the launch prefetch window 32–64 KB, so instruction lines past the window fetch from HBM at first use. The remedy reads the kernel's OWN TEXT AS DATA at launch: "the kernel's own TEXT made L2-hot from the DATA side at launch … a plain data load of one word per 128-B line of the kernel's code puts the line in L2; so every launch prefetches the whole text again" (layer.cu:33-38) — one converged warp, one 4-B load per 128-B line, `createpolicy.fractional.L2::evict_last` cookie, loads-only ("the arithmetic is untouched"), `__noinline__` so ptxas places the routine BEHIND the kernel body ("text ahead of the MoE phase would push it out of the launch prefetch window" :60-62), the text range bound by the host at module load via an ELF relocation retyped from `R_CUDA_DESCRIPTOR` to `R_CUDA_64` + `.text` size (:49-55). Two arms of the law: (a) **re-warm EVERY launch** — "the layers in between stream more normal-priority bytes than L2 holds (the expert prefetch first of all)" (:34-36); without warming the expert prefetch was a net loss ("switching it off made steps faster" — blog); (b) **spread the readers, never split the work** — nine CTAs each read every line because the blog measured that GB300's two dies each keep their own L2 copy. **Caveats carried in-rule (added at the verdict's round 1):** PORTABILITY — the ELF-relocation retype relies on UNDOCUMENTED toolchain behavior (the README itself pins `--compress-mode=none` on the layer images because "the host's code-prefetch patch edits the cubin's ELF before loading it, which needs the uncompressed image") and may break across ptxas/driver versions; ANTI-REGIME — the trick presumes instruction fetch is backed by the SAME L2 that data loads fill, verified on Blackwell/GB300 only and UNKNOWN on Apple GPUs (our own lanes). The schedule-keep anecdote folds here as a caveat: "the layer images carry unread constructs because removing them changes ptxas's schedule of the images, not the work, and measured 1-2 % slower per step at TP8" (README — dead constructs kept for the compiler's schedule). Blog magnitude experiment: two 100 KB straight-line blocks stitched = 19.5 µs each vs 12.4 µs solo; 20 KB + 100 KB fits → solo speed (root cause icache, explicitly NOT register spills).
2. **`dry-pass-icache-warm-before-real`** (D; B−, MANDATORY in-rule adjudication vs candidate 1 — compose: candidate 1 is the coarse L2 arm, this the fine SM-icache arm for latency-bound stretches). Run a latency-critical loop TWICE: first pass executes the same instruction addresses with waits/stores/publishes skipped — "The dry pass: cell 0's g1 epilogue body runs once ahead of it on the emit warp and the non-stager drainer warps (w8-w11), in the tables -> rows window, on the accumulator's garbage, with no waits and no arrives: the same instruction addresses, so every CTA's first drain finds its lines in the instruction cache" (moe.cuh:2479-2481); sites: g1 epilogue (moe.cuh:1532/:1557 `ci = -1 runs cell 0's body once more ahead of it`), the combine row and layer-final norm (next_layer.cuh:444, :163, :711 "to warm the instruction cache, then for real"). The `#pragma unroll 1` discipline is load-bearing: "unrolled, the dry pass would warm a copy the real pass never runs" (blog). This rule also carries the CODE-FOOTPRINT arm (the reviewer's relocation of the gpu_110 face — gpu_110 is an attention-exchange rule and must not become the retrieval hit for icache queries): "so loops that carry no per-element register state stay rolled (`#pragma unroll 1` …): the same per-thread sequence of copies, issues and waits, so the arithmetic is bitwise the unrolled loop's, in fewer bytes" (README) + the ~50 KB unroll delta; gpu_110 keeps a KIN pointer only. Blog magnitude: 0.5–1 µs per op.
3. **`speculative-expert-prefetch-prev-step-routing`** (H — MoE dispatch; C+/B−). One otherwise-idle warp reads the PREVIOUS STEP's routing ids ("reads this layer's routing ids from the PREVIOUS step (the binding's last top-k, read once with acquire; nothing of the predecessor grid), histograms the experts and L2-prefetches the shard packs (W1, W2 and their scale factors) of the most-routed experts that fit the L2 budget, spread over every CTA of the launch, under the attention phase, long before this step's router runs. Consecutive steps route alike, so the MoE phase's g1 / g2 weight streams mostly hit L2" — moe.cuh:2833-2837); budget as policy, not constant: 48 MiB → 14 experts at the TP8 NVFP4 shard, 4 when "the wide budget's traffic costs the post-attention window more than it saves the MoE" (:2851-2853); plus at router-landing: each block prefetches its first expert tile into L2 beside reading the table, and experts already in L2 go FIRST in the tile list (blog). Wrong guess costs bandwidth while the GPU is idle anyway; blog: ~0.2 ms of 5.3 ms. **MANDATORY in-rule adjudication set (expanded at the verdict's round 1):** gpu_31 ds4 (SSD tier + prompt-frequency signal), gpu_39 (grid-axis tile order — enumeration vs residency priority), **gpu_79 `expert-cache-write-path-regime-gated` + B94 `decayed-frequency-eviction-recency-*` + rust_perf `entries_35` (the host-resident two-list expert cache) + gpu_87's MoE-dispatch kin line** — all four share the PREMISE "consecutive steps reuse experts"; the four differentiators that keep this a rule: (a) GPU-L2 tier with NO explicit cache structure — fire-and-forget prefetch, no admission list, no eviction victim policy (B94/gpu_79/entries_35 all maintain a structure); (b) executed by an idle warp DURING the attention phase inside the same launch; (c) budget treated as policy keyed on the cost to the post-attention window; (d) L2-resident experts prioritized in the tile list.
