## GOAT lead — `batch-mixed-length-pads-to-longest-group-by-length` (rust_perf batching, BENCHABLE)

**The law (their own landed decision, UPSTREAM: present at the pin — decision content only, never a PR candidate):** a batched forward pass pads every row in the pass to the pass's longest row, so mixed-length workloads pay the max; grouping similarly-sized rows first (stable sort by the encoded row's length, within a BOUNDED lookahead of eight chunks — never a global sort) cuts padded work; results are restored to input order. Quotes (`.raw/laya/laya-rust/src/batch_prediction.rs`):

- :17-18 — "How many batches of states the `sort_by_length` lookahead spans. Bounds the tokenized lookahead independently of the input size, as Python does." / `const SORT_WINDOW_BATCHES: usize = 8;`
- :33-36 — "Group similarly sized encoded states within windows of eight batches, so each batch pads to a shorter maximum. Takes effect only with a `batch_size` greater than one and smaller than the number of states; otherwise it does nothing. Results keep input order. Changing the batch shapes can slightly change floating-point predictions near decision thresholds."
- :126-129 — "Without a reordering `sort_by_length` the windows are the chunks themselves. With one, each window spans eight chunks, its states are stably sorted by `row_len`, and the sorted states are cut into chunks."

README decision-content (the measured column): paired median 1.42× CLI / 1.77× server / ~1.48× ONNX / 2.15× synthetic on mixed-length workloads, 0 decision flips; and the honesty rider: a single pass has nothing to reorder, so the CLI "says so on stderr rather than printing a same-speed result".

**GOAT test:** (1) Benchable — an ORIGINAL Rust driver fixture where per-row work is real padded-width work (fill a padded buffer, fold it), unsorted vs 8-chunk-window stable-sorted; wall-clock + alloc axis on the existing validator, with the entries_17 standalone-preflight fallback pre-named. (2) Exact semantics — order-preserving restore, stable sort; per-row results bit-identical by construction. (3) Magnitude — work ∝ Σ_pass rows×max_len vs Σ rows×len; their 1.42–2.15× is source-reported provenance, never bars; our fixture's numbers are the claim. (4) Deterministic — yes. **All four pass.**

**Regime / anti-regime:** mixed-length batched work (encoding, scoring, padded dispatch of any kind); uniform-length or single-pass workloads are the Tie anti-regime; the FP-drift caveat (batch shape changes can flip near-threshold decisions) rides the decision content — the rule serves throughput only where decisions are not at thresholds, and the fixture keeps per-row outputs identical by only reordering.

**Dedup (live greps at HEAD, 3+ vocabularies):** `sort_by_length|length.group|pad.to.longest|longest.row` — ZERO owners. `group.by.size|size.group|bucket.by.size|sort.by.size` — zero. Adjacent-but-distinct, adjudicate in-rule at authoring: `persistent-kernel-length-bucketed-mechanism-ladder` (B110, kernel_opt — buckets rows by length to PICK A KERNEL MECHANISM; this rule reorders ROWS to cut PADDING WASTE before chunked dispatch — different axis, compose not merge); `bounded-batch-buffer-pool` + `channel-send-batching-unpark` (entries_86 — buffer recycle + wake batching, neither reorders); `batch-hash-probe-prefetch-two-pass` (entries_77 — two-pass hashing, not padding).
